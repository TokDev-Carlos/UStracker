INSTRUÇÃO DO PROPRIETÁRIO À IA EXECUTORA
Execute a criação do sistema UStracker do início ao fim usando o pacote PECSUS_UStracker_1_2_1_EXECUCAO.zip anexo. Este texto é um roteiro de comando para uma IA com acesso a arquivos e ferramentas; não é um programa que gera o sistema sozinho. O ZIP contém o plano, contratos, tarefas, casos de aceite e verificadores documentais. Não responda apenas com um novo plano. Implemente, teste, revise, empacote e entregue o sistema conforme os gates abaixo.

1. AUTORIDADE E ESCOPO
Use somente o PECSUS 1.2.1 como plano vigente. UStracker é um produto independente; ASCALPI e Automação de Artes são referências seletivas. Não reintroduza funcionalidades adiadas, dependências remotas, domínios desses sistemas ou instruções antigas. Não altere escopo nem enfraqueça segurança/aceite para obter PASS.
Leia 00_LEIA_PRIMEIRO.md, PONTO_DE_PARADA.json, 01_ESPECIFICACAO.md, 02_CONTRATOS.md, MATRIZ_ESCOPO_HISTORICO.csv, 04_VERIFICACAO_E_ENTREGA.md e 05_OPERACAO_E_CONTINUIDADE.md. TAREFAS.json é a fonte dos passos; 03_EXECUCAO_LINEAR.md é sua versão legível. CASOS_ACEITE.json é o catálogo de testes, não evidência de aprovação.

2. PRIMEIRA AÇÃO CONCRETA
Localize o ZIP anexo ou, se houver Google Drive conectado, a pasta Projeto UStracker/UStracker/plano. Extraia o pacote em uma pasta documental. Leia o verificador antes de executá-lo e rode, na raiz PECSUS_1_2:

python tools/validar_plano.py --root .

Guarde comando, saída integral, exit code, horário UTC e SHA-256 do ZIP e do MANIFESTO_SHA256.json. Exit code diferente de zero bloqueia uso do pacote: identifique a divergência; não regenere hashes apenas para esconder falha.
Não escreva código do produto na pasta do plano. Crie uma raiz de engenharia UStracker_Engenharia local, fora de diretório sincronizado/UNC/SMB, ou retome uma raiz existente após conferir identidade/checkpoint. Antes de modificar projeto existente, leia AGENTS.md e preserve alterações do proprietário.
Copie a semente PONTO_DE_PARADA.json para Estado/PONTO_DE_PARADA.json apenas no primeiro início. Em retomadas, preserve o Estado existente; nunca reinicie tarefas aprovadas sem invalidar evidências afetadas.

3. AMBIENTE E GATE INICIAL
Execute T01 primeiro. Perfil formal: Windows 10 22H2 x64. Host WPF/.NET Framework 4.8 x64 + WebView2; CPython 3.13.15 x64 embeddable e sqlcipher3 0.6.2 cp313 win_amd64, hashes definidos no contrato. SQLCipher precisa ser real, com cipher_version comprovado e chave errada/SQLite plaintext recusados.
Ferramentas de engenharia podem existir na máquina de build; usuário final não precisa SDK/Python/Node globais. Comprove o Runtime em Windows limpo. Fixe versões/hashes transitivos e registre SDK versus WebView2 Runtime separadamente.
Windows 11 é perfil adicional; execute quando disponível e registre seu resultado. Ausência de Windows11 não substitui nem bloqueia prova formal Windows10; jamais declare compatibilidade homologada sem execução.
Se estiver em Linux/macOS ou sem VM/estação Windows autorizada, faça a preparação documental e o código/testes independentes de T01 que forem executáveis, registre BLOCKED no gate nativo e pare antes de T02. Produza o pacote de retomada com os comandos exatos e a dependência faltante. Não use browser externo, SQLite plaintext, mock ou inspeção de código para substituir prova nativa.

4. EXECUÇÃO LINEAR OBRIGATÓRIA
Para T01 até T18, sempre nesta ordem:
a) Leia a tarefa inteira e todos seus casos, contratos e requisitos associados; confira PASS válido da anterior.
b) Escreva testes dirigidos aos cenários antes da implementação correspondente; registre falha inicial pertinente, sem inventar resultado.
c) Implemente funções/classes com limites claros: Python tipado/PEP8; C# compatível net48; JavaScript ES modules locais; SQL com constraints/transações; PowerShell compatível 5.1 quando usado nos scripts Windows.
d) Revise cada função pública: entradas, saída, exceções, autorização, concorrência, transação, precisão e efeitos laterais.
e) Integre serviço/repositório/API/UI e rode o gate completo da tarefa, incluindo testes nativos/performance quando exigidos.
f) Corrija defeitos bloqueantes agora e repita os testes afetados e dependentes; não reduza teste ou requisito para aceitar falha.
g) Grave evidências reais e checkpoint atomicamente. Só avance quando todos os casos obrigatórios atuais da tarefa estiverem PASS com evidência válida.
Não peça autorização a cada arquivo ou etapa já abrangida por esta execução. Continue autonomamente em decisões locais reversíveis. Solicite informação somente diante de bloqueio real de acesso/ambiente/decisão não resolvida; não invente acesso ou resultado.

5. COMANDOS DE GATE QUE T01 DEVE IMPLEMENTAR
Da raiz da engenharia, em PowerShell 5.1:

& .\.venv\Scripts\python.exe tools\verify.py --task T01 --native --profile win10_22h2 --evidence-dir Evidence
if ($LASTEXITCODE -ne 0) { throw 'T01 bloqueada: consultar Evidence/T01' }

Para a tarefa corrente, substitua T01 pelo ID real. --task nunca omite teste obrigatório só porque --native não foi escrito. --explain descreve testes e não aprova nada. O harness não existe no plano como sistema pronto: ele é um entregável de T01 a ser implementado e provado.
Ao final:

& .\.venv\Scripts\python.exe tools\verify.py --integration --profile win10_22h2 --evidence-dir Evidence
if ($LASTEXITCODE -ne 0) { throw 'Integracao completa reprovada' }
& .\.venv\Scripts\python.exe tools\release_gate.py --candidate Dist\Candidate --evidence-dir Evidence
if ($LASTEXITCODE -ne 0) { throw 'Release gate reprovado' }

Implemente release_gate.py com esses argumentos e faça-o conferir evidências, hashes, cobertura de itens históricos e ausência de bloqueantes. Não confunda esse gate do produto com tools/validar_plano.py, que só valida documentos.

6. INVARIANTES QUE NÃO PODEM SER RELAXADAS
- PUBLIC só recebe projeção allowlist; dados privados não chegam ao navegador para depois serem borrados. Dirty marker fail-closed, autorização no backend, CSRF/Origin e capacidades de Shell reais.
- Exatamente três slots ADMIN individualizados. Setup/login funcionam antes do DB privado; reset é enrollment, nunca senha temporária escolhida por outro administrador.
- Production/Test: datasets/keys/mídia/jobs/exports separados, AuthStore compartilhado. Reset Test não apaga administradores nem produção.
- X fecha/revoga a Shell; backend permanece. Ao terminar última sessão, jobs privados pausam em checkpoint e keys/DBs fecham. Nova Shell abre PUBLIC com profile novo.
- Dinheiro: centavos inteiros/Decimal, nunca float. Pagamento parcial/crédito/aplicação/estorno não duplicam caixa e preservam o histórico pelas datas dos eventos. Reversão de origem desfaz crédito já utilizado transacionalmente.
- Uma estação escritora no protocolo; transferências autenticadas, geração e origem TRANSFERRED antes da entrega. Não prometer revogação remota de clones offline; recovery exige retirar cópias antigas de uso.
- Backup deve usar framing/AAD completos de 02_CONTRATOS.md e snapshot consistente. Restore local não reativa senha antiga. Recovery export é ação separada e protegida.
- Update: QUIESCED antes do backup, depois staging/migração, switch do par release/dataset, VERIFIED e ACCEPTED antes de liberar writes. Rollback nunca apaga lançamentos posteriores silenciosamente.
- Integrações adiadas retornam disabled/501 sem rede. Não publicar site, mandar mensagens, criar credenciais cloud ou configurar GitHub remoto como requisito da V1.
- Chaves e dados reais não entram em logs, fixtures, snapshots técnicos ou release. Chave de assinatura de teste é segregada; assinatura produtiva exige chave controlada pelo proprietário.

7. EVIDÊNCIA, MUDANÇA E RETOMADA
Use Estado/PONTO_DE_PARADA.json e Evidence/<Txx>/result.json na engenharia. Registre requisito→H-item→arquivo/função→caso→evidência; para cada comando: comando literal, cwd, UTC, exit code, stdout/stderr, OS/build/runtime e hashes de artefatos. Não marque PASS pelo nome de arquivo ou contagem de testes.
Antes de encerrar uma sessão ou após uma etapa, registre: última etapa aprovada, etapa atual, casos executados/não executados, blockers, alterações pendentes, hashes, comandos para continuar e próxima ação exata. Grave arquivo temporário e promova atomicamente; mantenha checkpoint anterior.
Se surgir contradição real: registre-a, corrija primeiro o contrato vigente e tarefas/matrizes/casos afetados, gere nova revisão documental auditável e invalide as provas dependentes. Não misture versões. O plano aprovado original permanece preservado.
Falha de segurança, dados, valores, isolamento, backup/update, requisito obrigatório ou integração central é BLOCKING. Somente cosmética sem prejuízo funcional entra AJUSTES_FUTUROS.log, com reprodução, impacto e versão-alvo. Ambiente indisponível é BLOCKED/NAO_EXECUTADO, nunca PASS.
